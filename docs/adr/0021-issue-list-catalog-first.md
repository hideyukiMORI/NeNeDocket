# ADR 0021 — 課題管理表の項目は「カタログ先行」: 型と状態の区分はコードで固定し、台帳ごとに変えるのは有効にする項目と表示名だけ

- 状態: **受理**（Issue #106・施主 2026-10-22「全部推しでいいよ」）
- 日付: 2026-10-22
- Issue: #106（方針）・#107（段階 0）
- 影響する規則: FR-001 / FR-002 / FR-012 / FR-017 / ARC-001 / ARC-011 / ARC-013 / QLT-008 / QLT-010 / ADR 0004 / ADR 0006

## 文脈

施主は日本の「課題管理表」（Excel・1 行 1 課題・No／起票日／分類／課題／原因／対応策／担当／期限／優先度／ステータス／完了日／備考・定例で読み合わせ・印刷）を想定し、「設定で足し引きして参考の使い方をある程度以上カバーしつつ、速度・安定性・レイアウト・ユーザビリティを確保したい」と求めた。いまの項目は固定の 7 つ（題名・本文・状態・担当・期限・ラベル・並び順）で、足し引きの方針が無い。

調査（[docs/design/2026-10-22-issue-list-research.md](../design/2026-10-22-issue-list-research.md)）で、核の列は各国で同じ・違いは「何を 1 枚にまとめるか」と「承認をどこに置くか」、項目を増やしすぎると遅くなることは Jira と Notion が公式に認めている、と分かった。4 人の専門家ペルソナの提案と相互批評の結論は [docs/design/2026-10-22-issue-list-catalog-first.md](../design/2026-10-22-issue-list-catalog-first.md)。

## 決定

1. **項目の型はコードで固定する。** 足せる項目は、ID を予約した「カタログ項目」（約 20・分類・優先度・原因・対応策・再発防止策・確認者・回答期限・影響度・決定日・管理 No など）を core の閉じた `Field` に足して持つ。台帳ごとに変えられるのは、どのカタログ項目を有効にするかと表示名だけ。利用者が型を選んで項目を作る機能は**入れない**（カタログで足りないと実際の利用で分かった名前を、カタログに足す）
2. **自動の項目を導く。** 起票日・起票者・完了日・更新日はジャーナルから導き、新しいデータを持たない
3. **状態の区分を 6 つに固定する**（未着手・対応中・確認中・保留・完了・中止）。台帳ごとに変えられるのは名前だけ。いまの 3 つ（`Open` / `InProgress` / `Done`）はその部分集合として移す
4. **上限はコードの定数。** 表に出す項目は合計 24、長文は 4、選択肢は 1 項目 32。FR-017 の数値を最大の負荷（10 万件 × 24 項目すべてに値）で測り、超えたらゲートでなく上限を下げる
5. **型・共有ビュー・定例の基準点は台帳の操作**として署名付きでジャーナルに追記し、普通の操作と同じ全順序で併合する（ADR 0004）。個人の見た目は設定ファイルのまま
6. **作らない**: 数式・関連・集計、複数選択、型の変更、項目ごとの閲覧権限、台帳を通した自動の連番、利用者の付けた名前の自動翻訳、カンバン・ガント、通知、行ごとに違う高さ、xlsx の書き出し（要望を見てから決める）
7. **番号は頭の 4 桁をアカウントの略称に変えて見せる**（例 `森-12`）。台帳を通した連番は約束しない。移行した台帳の旧番号はカタログの「管理 No」
8. **定例の基準点は誰でも打てて、台帳に 1 本だけ共有する**（最後に打った基準が全員の基準）。権限を有効にした台帳では編集者だけ
9. **段階で入れる**: 0 = 自動の項目・色の規則・番号の略称（データの形を変えない）／1 = 台帳の版 2・状態の区分・カタログ項目・プリセット 5 種・折り返し・共有ビュー・CSV の往復／2 = 定例の差分・印刷用 HTML・見出しの絞り込み／3 = 承認の門・残りのプリセット。現地化の順は日本 → 韓国・台湾 → 欧米

## 強制

- planned: すべて。段階 0 は Issue #107。段階 1 以降は段階ごとの Issue と ADR（カタログ項目と予約 ID・台帳の版 2・状態の区分・自動の項目・共有ビュー・定例の基準点・CSV と印刷・メモリの予算・連番を約束しない・遷移の権限）で、測れるものから active にする
- 上限の定数と最大の負荷の測定は、段階 1 で CI のゲートにする（planned）

## 結果

- 得たもの: 日本の様式（7〜15 列）をプリセットで覆いながら、型が閉じているので併合・索引・検索・翻訳・レイアウトが壊れにくい。新しい依存は要らない
- 失うもの: 利用者が自由に項目を作れない。カタログに無い名前は待ってもらう。Airtable 型の「何でも足せる」を求める人には合わない
- 残る穴: 台帳の版 2 で、古い実行ファイルが混ざった台帳の扱い（止まって示す）を段階 1 で決める。調査は二次資料を含む。現地化の順の理由は推測

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| 何でも足せる（Airtable / Notion 型・型を選んで項目を作る） | 項目の増加が遅さと使いにくさの主因（Jira・Notion の公式文書）。同時に 2 人が項目を作る・型を変える併合が難しくなる。上限も守りにくい |
| 固定のまま（Linear 型を徹底） | 日本の様式（原因・対応策・確認者・完了日）を覆えず、施主の目的を満たさない |
| 状態の集合を台帳ごとに自由にする | 絞り込み・色・完了率・完了日・承認の門が「区分」に頼るので、区分を固定して名前だけ変えるほうが壊れない（Linear の設計と同じ） |
