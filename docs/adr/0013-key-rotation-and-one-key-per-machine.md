# ADR 0013 — 鍵は 1 台に 1 つ。同じ人の 2 台目は別のアカウントで、鍵の交代は持ち主が署名した引き継ぎで表す

- 状態: **受理**（施主 2026-10-21「推しで」・Issue #51 で実装）
- 日付: 2026-10-21
- Issue: #45 / #51
- 影響する規則: ARC-009 / ARC-010 / FR-009 / FR-010 / FR-014。ADR 0010 の「残る穴」の 2 つ

## 文脈

ADR 0010（Issue #29）で、アカウントは設定フォルダの `account.v2.txt` に秘密鍵を持ち、台帳の `keys/<account>.v1.pub` に公開鍵と名前を置く。鍵の失効・交代と、同じアカウント ID を 2 台で使ったときの扱いは決めていない。

いま起きること（実測・gate-proofs 第 22 節）:

- 同じ ID の 2 台目が台帳を開くと、`keys/` の公開鍵が手元と違うので `AdmissionReport::key_mismatch` が立ち、画面に「台帳にある自分の公開鍵が手元と違います」と出る。2 台目の署名は 1 台目の公開鍵で通らず、読み手全員が捨てる
- 鍵を失くした人（設定フォルダを消した・OS を入れ直した）は、新しい `account.v2.txt` が新しい ID と鍵で作られるので、別の人として台帳に現れる。古い ID の行は残り、「誰が」は古い名前のまま
- 持ち主が鍵を失くすと、`permissions.v1.txt` に署名できる人がいなくなり、権限を変えられない

設定フォルダは利用者ごと・機械ごとなので、ID と鍵の対はもともと「機械の上の人」を指している。

## 決定（提案）

**鍵は 1 台に 1 つで、アカウント ID と対にする。同じ人の 2 台目は別の ID・別の鍵で参加し、`keys/` の名前で同じ人と分かるようにする（ID の複製はしない）。鍵の交代は「古い ID を新しい ID が引き継ぐ」と持ち主が `permissions.v1.txt` に書いて署名し、読み手は引き継いだ ID の行を同じ人として扱う。失効は編集者から外すだけで足りる。**

1. **複製しない。** `account.v2.txt` を別の機械へ写すことは支持しない。写した結果の `KeyMismatch` は今のまま示す（FR-014）。文書（README）に「設定フォルダは機械ごと。写さない」と書く
2. **2 台目。** 別の ID で参加する。履歴の「誰が」は `keys/` の名前なので、同じ名前なら同じ人に見える。持ち主は 2 台目の ID も編集者に加える（画面の参加者の段か `--allow`）
3. **引き継ぎ。** `permissions.v1.txt` に `succeeds = <新しい ID>: <古い ID>` の行を足す（`--succeed <新> <旧>`）（版は 1 のまま・知らない鍵を前の読み手は拒むので、**読み手を先に更新する**。拒まれる間は `BadPermissionsFile` で起動が止まる＝黙って落ちない）。持ち主が書いて署名する（画面では参加者の段の編集行の「引き継ぎ先」・Issue #54）。古い ID が編集者なら新しい ID が編集者になり、古い ID の入っていたグループに新しい ID が入り、古い ID は一覧と参加者の段から外れる（古い ID は引き継いだ ID の役を持つ）。読み手は `succeeds` を辿って、古い ID の課題の作成者・担当・履歴の「誰が」を新しい名前で出す。古い ID の行は捨てない（署名は古い公開鍵で検証したまま）
4. **持ち主の交代。** `docket.v1.txt` の `owner` を書き換えられるのは今の持ち主だけ（`--owner <新しい ID>`）。交代の直後の `permissions.v1.txt` は前の持ち主の鍵で署名され `handover = <前の持ち主>` の行を持つ。読み手は持ち主の鍵か、`handover` の鍵で本物と確かめる。新しい持ち主の最初の操作で署名し直され `handover` は消える。持ち主が鍵を失くしたら、台帳のフォルダを書ける人が `docket.v1.txt` を手で直す（権限は「書けるフォルダ」より強くない・ADR 0010 の守る相手）。このとき `permissions.v1.txt` は新しい持ち主の最初の操作で署名し直す（持ち主の欄が自分なのに署名が通らないファイルは、持ち主だけが中身を受け入れて署名し直せる）
5. **失効。** 編集者から外す（`--disallow`・参加者の段）。以後の行は捨てられ、過去の行は残る。鍵の失効の一覧（CRL）は持たない

## 強制

- active: `permissions_file` が `succeeds` と `handover` を読み書きし、`Permissions::resolved` が引き継ぎを辿り、`names` が引き継いだ名前を出すテスト（Issue #51・gate-proofs 第 32 節）
- active: `--owner` が今の持ち主以外で失敗し、交代の直後は前の持ち主の署名（`handover`）で通り、新しい持ち主の最初の操作で署名し直されるテスト（Issue #51）
- 不能: 設定フォルダを写さないことは文書で言うだけ。写せば `KeyMismatch` が出る（active・Issue #29）

## 結果

- 得られるもの: 鍵を失くしても ID を変えるだけで続けられ、持ち主の 1 行で前の名前がつながる。鍵の複製という弱い経路を作らない
- 失うもの: 同じ人が 2 つ以上の ID を持つ。参加者の段に同じ名前が並ぶ（引き継ぎを書くまで）
- 残る穴: 持ち主の鍵の紛失は「フォルダを書ける人が直す」で、署名の外にある。本人が引き継ぎを署名する案（下の却下）より手間が持ち主に寄る

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| `account.v2.txt` を機械間で写す（同じ ID・同じ鍵） | 秘密鍵が共有フォルダや USB を通る。2 台で同時に書くと論理時計が重なり、同じ `OpId` の別の操作ができる（併合が最初の 1 つしか数えない・ADR 0004） |
| 本人が新しい鍵で「古い ID を引き継ぐ」行を署名する（持ち主を介さない） | 古い鍵を失くした本人は古い ID の所有を証明できない。誰でも他人の古い ID を名乗れる |
| 鍵ごとの失効の一覧（CRL） | 編集者から外せば足りる。一覧は持ち主の署名が要り、`permissions.v1.txt` と二重になる |
| 機械 ID を別に持ち、アカウント ID と機械 ID の対で署名する | ID が 2 つになり、`keys/`・ジャーナルの行・履歴の全部が変わる。2 台目を別のアカウントにすれば同じことが今の形で済む |
