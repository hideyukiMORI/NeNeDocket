# ADR 0004 — 台帳はアカウントごとの追記専用ジャーナルの併合。サーバもロックも無い

- 状態: 受理
- 日付: 2026-10-21
- Issue: #1
- 影響する規則: ARC-001 / ARC-004 / ARC-007 / ARC-008 / ARC-009 / RS-016 / QLT-008 / QLT-013

## 文脈

施主の要件（2026-10-21）は次の 6 つで、互いに引っ張り合う。

1. 落ちても数秒前の状態が残る（FR-004）
2. Undo / Redo（FR-005）
3. 版管理＝履歴（FR-006）
4. 複数アカウントの同時編集。ネットワークフォルダを指定すればチームで安全に編集できる（FR-007 / FR-011）
5. コンフリクトも安心（FR-008）
6. 権限とグループ。設定しなければ誰でも編集モード（FR-010）

共通の制約は**サーバが無い**こと。同期は OS のファイル共有（SMB）に任せる。

SMB の上で信用できないもの:

- **ロック。** SMB の byte-range lock と oplock はクライアントと鯖の実装に依り、WSL2 の DrvFs や Samba の設定で挙動が変わる。SQLite の公式文書も「ネットワークファイルシステムの上での同時アクセスは壊れうる」と明記している
- **上書きの原子性。** `rename` による置き換えは同じ共有の中なら概ね原子だが、別クライアントのキャッシュがいつ新しい内容を見るかは保証されない
- **1 つのファイルへの複数の書き手。** 2 台が同じファイルに追記すると、末尾が交錯するか片方が消える

信用できるもの:

- **1 つのファイルに書くのは 1 台だけ**なら、追記は（その 1 台から見て）順序を保つ
- 他のクライアントは、遅れはあっても**いずれ**伸びた分を読める。読めるのは完全なレコードか、書きかけの末尾かのどちらか

これは「各自が自分のファイルにだけ追記し、読み手が全部を併合する」形がちょうど噛み合う。
Undo・履歴・落ちても残る、の 3 つも、**操作の列を追記で持つ**ことで同じ 1 つの仕組みから出る。

## 決定

**台帳は、アカウントごとの追記専用ジャーナルの集合である。いまの状態はそれを決定的に併合した派生値であり、正本ではない。**

1. **置き場。** 台帳 = フォルダ。`journal/<account-id>.v1.log` にアカウントごとのジャーナルを置く。`docket.v1.txt` に台帳の版と名前を置く。他のファイルは作らない（スナップショットは別の ADR）
2. **書き手は 1 つ。** 各プロセスは自分のアカウントのジャーナルにだけ書く。他人のジャーナルは読むだけ。**同じアカウントで 2 台から同時に開くことは守らない**（FR-014 で示す。将来は機械 ID を足す）
3. **レコード = 操作（op）。** 1 行 1 レコード。内容は: 論理時計・壁時計（表示用）・アカウント ID・操作 ID・課題 ID・項目・新しい値・（あれば）打ち消す操作 ID。テキストで、1 行の末尾に長さか検査和を置いて書きかけを見分ける（形式の細部は `store` の版 1 が持つ）
4. **追記だけ。** ジャーナルを書き換えない・縮めない・並べ替えない。Undo は**逆の操作を追記**する。削除も「削除した」という操作を追記する
5. **同期。** 操作は即座に自分のジャーナルへ追記し、2 秒以内（決め打ちしない）か操作が止まった時点で fsync する。落ちたときに失うのは最大この幅
6. **併合は純関数。** core の `merge` が全ジャーナルの操作を（論理時計・アカウント ID）の全順序に並べ、課題ごと・項目ごとに**最後の操作が勝つ**。負けた操作は履歴に残る。入力が同じなら出力は同じ（ARC-007）。時刻も乱数も読まない
7. **論理時計。** Lamport 時計。自分の操作は、自分がこれまでに見た最大の時計 + 1。壁時計は順序に使わない（機械ごとにずれる）
8. **読み直し。** 他人のジャーナルは、伸びた分だけを 3 秒ごと（決め打ちしない）と、自分の操作の前に読む。読んだ末尾が壊れていれば（書きかけ）そのレコードを飛ばして次回また読む
9. **壊れたレコード。** 自分のジャーナルの末尾が壊れていれば（落ちた直後）、そのレコードを捨て、捨てたことを示す（FR-014）。真ん中が壊れていれば、そのアカウントのそれ以降を読めないものとして示す。**黙って直さない**
10. **権限。** 権限を有効にしない台帳では、アカウント ID は名乗りであり、なりすましを防がない。権限を有効にした台帳では各レコードに署名が付き、読み手が検証して通らないレコードを捨てる（示す）。鍵・署名の方式と依存は別の ADR
11. **版。** ジャーナルの形式は版を持つ（`.v1.log`）。新しい版の書き手は古い読み手が読めるレコードを壊さない。壊すなら拡張子の版を上げ、古い読み手には「読めない版」として示す（ARC-009）

## 強制

- **planned**: 併合の決定性は core が `#![no_std]`（CNF-007）であることと、同じ操作の集合を別の順で読むテスト（QLT-008・ADR 0003 の 7）で見る。追記だけであることは `store` のテスト（書いたファイルの先頭が変わらない）で見る。Issue #2 以降
- **不能**: 「ジャーナルを書き換える経路を作っていないか」はレビュー事項（DEVELOPMENT_WORKFLOW 第 7 節の拒否項目）。SMB の上で本当に壊れないかは施主の共有で確かめるまで「動く」と書かない（QLT-013）

## 結果

得られるもの:

- 落ちても残る・Undo / Redo・履歴・同時編集・コンフリクトの 5 つが、**追記と併合の 1 つの仕組み**から出る。第 2 の経路が要らない（ARC-001）
- ロックに依存しないので、SMB・Samba・DrvFs・USB メモリ・Dropbox のフォルダでも同じ形で動く（同期の遅れはあっても壊れない）
- 自分のジャーナルは自分の機械が書くので、共有が落ちていてもローカルでは操作できる。共有が戻れば追記分が見える
- 併合が純関数なので、1 万件・1 年分のジャーナルの併合を OS 無しで測れる（FR-017）

失うもの・残る穴（**正直に**）:

- 🔴 **本文の同時編集は項目単位で勝敗が付く。** 2 人が同じ課題の本文を同時に書き換えると、片方の本文が丸ごと負ける（履歴には残る）。行や文字の併合（CRDT の文字列）はしない。「コンフリクトも安心」は「失われない」の意味であり、「自動で両方が活きる」ではない
- 🔴 **壁時計は信用しない。** 履歴の「いつ」は書いた機械の時計で、ずれていればずれたまま出る
- 🔴 **同じアカウントを 2 台で同時に開くと壊れる。** 守るのは別の Issue（機械 ID を ID に足す）
- 🔴 **権限を有効にしなければ、なりすましは防げない。** ファイルを読める人は、他人の ID でレコードを書けてしまう（ファイルを直接編集すれば）。それでも**他人のジャーナルを書き換える経路はアプリには無い**
- 🔴 **ジャーナルは伸び続ける。** 1 年分の併合が 1 秒を超えたらスナップショット（併合済みの状態を別ファイルに書き、それ以降のジャーナルだけ読む）の ADR が要る。スナップショットも「追記だけ」の原則の中で設計する（元のジャーナルは消さない）
- 🔴 **SMB の読み直しの遅れ。** 他人の操作が見えるまで数秒かかりうる。見えない間に同じ項目を変えれば、論理時計の順で勝敗が付く。これは仕様（FR-008）であり、不具合ではない
- 併合の規則（最後が勝つ）は単純すぎるかもしれない。並び順の項目（課題の並び替え）は、全員が同じ列を動かすと順序の意図が壊れうる。実装して窮屈なら項目ごとの規則を ADR で足す

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| 1 つの共有ファイルをロックして上書きする | SMB のロックは信用できない。壊れた書き込みが全員に波及する。落ちたときに「数秒前の状態」が残る保証が無い |
| SQLite を共有フォルダに置く | SQLite 自身がネットワークファイルシステムの上での同時アクセスを「壊れうる」と明記している。依存も 1 つ増える |
| サーバ（HTTP / gRPC）を立てる | 施主の要件に反する。「ネットワークフォルダを指定すれば」が全て |
| CRDT のライブラリ（automerge / yrs 等） | 依存の木が大きく、形式が不透明で、ARC-009 の版管理を自分で持てなくなる。本文の文字単位の併合は要件に無い |
| 自前で文字列 CRDT を書く | 要件に無い（「コンフリクトも安心」は「失われない」）。要るなら後から項目単位の規則を ADR で変えられる |
| Git を裏で使う | Git は SMB の上の同時 push を守らない。依存が重く、利用者に Git を要求することになる |
| 壁時計で順序を決める | 機械ごとにずれる。同じ入力から同じ出力が出ない |
| 操作でなく状態のスナップショットを定期的に書く | Undo と履歴が別の仕組みになる。同時編集の併合ができない。「数秒前」がスナップショットの間隔に縛られる |
| 1 つのアカウントに 1 ファイルでなく、操作ごとに 1 ファイル | SMB でのファイル作成は遅く、1 万ファイルの一覧が重い。追記は 1 ファイルで十分 |
| 最初から署名を必須にする | 「設定しなくても誰でも編集モードで使える」に反する。依存も先送りできる |
